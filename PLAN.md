# OpenPdfEdit — Product & Implementation Plan

**Status: M0, M2, M3, M4, M5, M6, M7, M8, M9 implemented and tested; M1 (viewer chrome) substantially covered as a side effect of M2's UI work. M3's encrypt/decrypt scope is blocked (see below), everything else in M3 is done. M4 forms-fill (Text/Checkbox verified, RadioButton best-effort, ComboBox/ListBox read-only) and M4 OCR (Tesseract-only, English-verified) are both done. M5 signature *inspection* is done — cryptographic verification is deliberately out of scope for this pass, see below. M5 redaction (true content removal, PDFium-verified) is done. M6 license plumbing scaffold is done — real Ed25519 verify/import, no OpenApps checkout backend (doesn't exist yet), no feature gating (still deferred per decision log). M7's MVP (single-text-run substitution + image reposition, PDFium-verified) is done — full glyph-accurate reflow/font-subsetting is explicitly out of scope, see below. M8's form-*creation* half is done and PDFium-verified; the PAdES-signing half is deliberately deferred for the same crypto-immaturity reason M5's verification was — see below. M9's search-and-redact PII patterns, document compare (text + pixel modes), batch pipelines, and headless CLI are done and PDFium-verified; PDF/A convert/validate and full release engineering are deliberately out of scope for this pass — see below. 1.0-and-beyond scale work is otherwise complete.**
*Date: 2026-08-01. Synthesized from four deep-research reports in `docs/research/` (Acrobat analysis, competitor landscape, Rust stack evaluation, OSS borrow-map). Read those for sources; this document is the decisions.*

**Implementation status (2026-08-01):**

- **M0 (foundations):** Cargo workspace (11 crates + CLI + Tauri app), `openpdfedit-engine` (Engine trait, PDFium backend, dedicated render thread, LRU tile cache), Tauri 2 + Svelte 5 desktop shell with a real `tile://` custom-URI-scheme pixel path (no JSON/base64 for pixels), a virtualized-scrolling zoomable multi-page viewer with open-file/zoom toolbar, GitHub Actions CI (mac + Windows + license-policy jobs), `cargo-deny` license gate, a 20-file pdf.js-derived test corpus with regression tests in both `openpdfedit-doc` and `openpdfedit-engine`, and a `cargo-fuzz` target for `openpdfedit-doc` (verified: 33k+ executions, zero crashes, ASan-instrumented).
- **M2 (annotations, done ahead of sequence since it was the natural next vertical slice):** `openpdfedit-doc` incremental-save pipeline (`lopdf::IncrementalDocument`, diff-based, chains correctly across repeated saves, verified to preserve a prior signature's bytes untouched); `openpdfedit-annot` with Highlight/Underline/StrikeOut/FreeText/Ink, real PDF appearance-stream generation (self-contained per-annotation `/Resources`, following pdf.js's `AnnotationEditorLayer` pattern), cross-validated by actually rendering the output through real PDFium (not just re-parsing with our own reader); Tauri commands (`add_annotation_cmd`, `list_page_annotations`) with real end-to-end test coverage (disk I/O, engine-handle rotation, PDFium render, all exercised — not mocked); Svelte markup toolbar + pointer-gesture capture (drag-rect for highlight/underline/strikeout, click for note, freehand for ink) + a comments panel.
- **M3 (page organization):** `openpdfedit-doc` gained single-document page ops (`rotate_page`, `delete_page` with correct ancestor `/Count` decrementing, `reorder_pages` which flattens the page tree, `set_crop_box`), all incremental-save-compatible and cross-validated through real PDFium after chained edits. New `openpdfedit-pages` crate for cross-document ops (`merge` — object renumbering ported from lopdf's own `examples/merge.rs`, `extract_pages`), which are necessarily full-document rewrites, not incremental saves (see that crate's module doc for why). A shared `commit_mutation` helper in the Tauri layer (`apps/desktop/src-tauri/src/lib.rs`) implements the common "mutate → save → rotate the render handle" sequence used by both annotations and page ops. Six new Tauri commands (`rotate_page_cmd`, `delete_page_cmd`, `set_crop_box_cmd`, `move_page_cmd`, `merge_documents_cmd`, `extract_pages_cmd`) plus a Svelte Pages panel (`PagesPanel.svelte` + `PageThumb.svelte`): per-page thumbnail, rotate/delete/move-up/move-down, a prompt-based crop-box input (no drag-rectangle mode — see that component's comment for why), page-selection checkboxes feeding "Extract selected", and a "Merge PDFs…" flow that opens a native multi-file picker and save dialog.
- **M3 security (encrypt/decrypt): BLOCKED, deliberately unshipped.** `lopdf::Document::encrypt()` (V4/AES-128 and V5/AES-256) unconditionally forces cross-reference-*stream* output regardless of `SaveOptions`, and reloading that output loses most/all of the object graph — confirmed via multiple independent minimal reproductions built from lopdf's own public API. This overlaps with open upstream issue lopdf#479, but is broader: that issue's claimed workaround (plain `save()`) did not reliably work in testing on lopdf 0.44 either. Rather than ship encryption that could silently corrupt a user's document, the feature was removed after implementing it; `openpdfedit-doc`'s module doc has the full writeup and three forward paths (wait for an upstream fix, hand-roll the Standard Security Handler with RustCrypto, or shell out to qpdf).
- **M4 forms fill (AcroForm via PDFium formfill):** new PDFium-backed methods on `PdfiumEngine` (`list_form_fields`, `fill_form_fields`, `save_document`) — deliberately *not* on the `Engine` trait, since form-filling is a PDFium-specific write capability, not a rendering primitive a future backend would need. Unlike annotations/page-ops, this write path mutates PDFium's own already-open document in place rather than going through `openpdfedit-doc`'s lopdf model (see `openpdfedit-engine`'s form-fill module doc for why). Two new Tauri commands (`list_form_fields_cmd`, `fill_form_fields_cmd`) plus a Svelte Forms panel (`FormsPanel.svelte`) that groups widgets by field name, editable inline (text on blur/Enter, checkbox/radio on change). **Text and Checkbox fill are verified end-to-end** (fill → save → reopen → read back the same value through a fresh handle, with real PDFium). **RadioButton fill is best-effort, not verified reliable**: confirmed via an independent PDF library's raw structural dump that `pdfium-render`'s `set_checked()` writes `/V` onto the *widget's own* dict rather than the shared parent field a proper multi-option group uses, and the read path doesn't reliably resolve grouped state either — documented in `PdfiumEngine::fill_form_fields`'s doc rather than silently shipped as fully working. **ComboBox/ListBox selection is not settable at all** — `pdfium-render` 0.9.3 exposes only read access to combo/list options, no public selection API.
- **M4 OCR (searchable text layer via Tesseract):** new `openpdfedit-ocr` crate — render a page via `openpdfedit-engine` at scan DPI, shell out to a locally-installed `tesseract` binary (subprocess, not an FFI binding — see that crate's module doc for why) for word-level text + pixel-space bounding boxes, then append an invisible ("sandwich," text render mode 3) text layer onto the page's content stream via a new `openpdfedit-doc::Document::append_content_stream` primitive (additive — never touches the existing visible content, handles `/Contents`/`/Resources` being either direct or indirect). One new Tauri command (`ocr_document_cmd`, blocking — no per-page progress reporting yet) plus an "OCR document" toolbar button. **Verified end-to-end with a real `tesseract` binary and real PDFium**: a page rendered with real visible text is OCR'd, the invisible layer appended and incrementally saved, then reopened through a fresh PDFium handle and confirmed to have *more* PDFium-extractable characters than before — proof the output is genuinely searchable by PDFium's own text engine, not just structurally present per this crate's own bookkeeping. Scoped to Tesseract + `eng`/ASCII text only for this pass — platform-native OCR (macOS Vision, Windows.Media.Ocr) is deliberately not attempted, since a Windows-only engine can't be verified from this single macOS dev environment (same reasoning as every other "don't ship what can't be tested here" call in this log); non-ASCII OCR output is skipped rather than mis-encoded, since full Unicode needs `ToUnicode` CMap infrastructure not built yet.
- **M5 signature inspection (not cryptographic verification — a deliberate scope decision):** new `openpdfedit-sign` crate, structural-only: `find_signatures` scans a PDF's raw object graph via `lopdf` for every `/Type /Sig`/`/Type /DocTimeStamp` dictionary and reports what it declares (`/SubFilter`, `/Reason`, `/Name`, `/M`, `/ByteRange`, `/Contents` length) plus one purely mechanical structural check — does `/ByteRange` have the `[0, a, b, len-b]` shape a well-formed signature must. **Deliberately does not implement actual cryptographic verification** (CMS/PKCS#7 SignedData parsing, RSA/ECDSA signature check, X.509 chain building, AATL/EUTL trust-anchor validation, OCSP/CRL revocation): investigated RustCrypto's `cms` crate (the natural fit) and found it still pre-release (`0.3.0-pre.2`) as of this writing — a signal this isn't a quick wire-up even with mature crypto primitives underneath. Given the failure mode of a subtly wrong verification isn't "reduced functionality" but "the app tells a user a tampered or forged document is validly signed," this got the same treatment as the lopdf encryption bug: don't ship it half-built. One Tauri command (`list_signatures_cmd`) plus a header badge ("⚠ N signature(s) (unverified)") that shows structural details on click via a dialog that leads with "NOT CRYPTOGRAPHICALLY VERIFIED" — the DTO's `isVerified` field is hardcoded `false` end-to-end so neither the wire format nor the UI can be misread as a validity claim.
- **M5 redaction (true content removal — the actual security property, not a black box painted over live data):** new `openpdfedit-redact` crate implements a coarse content-stream interpreter: tracks the graphics state (CTM via `q`/`cm`/`Q`, text position via `BT`/`Tm`/`Td`/`TD`/`T*`) through a page's content stream and **drops every operator whose paint area overlaps the redaction rect entirely** — text (`Tj`/`TJ`/`'`/`"`, approximate bounding box from font size × character count), images (`Do`, unit-square-through-CTM bounding box), and vector paths (`m`/`l`/`c`/`v`/`y`/`re` + a paint op, point-cloud bounding box) — then overlays a solid box on top as a visual belt-and-suspenders. Deliberately conservative in the direction of removing slightly more than the exact minimum (approximate text/curve extents can only be *larger* than the true rendered extent, never smaller) rather than risking leaving any redacted-looking content actually recoverable. New `openpdfedit-doc` primitives (`page_content_bytes`, `set_page_contents`) support reading/wholesale-replacing a page's content stream. One Tauri command (`redact_page_cmd`, via the same `commit_mutation` pattern as annotations/page-ops) plus a "Redact" tool reusing the existing drag-rectangle gesture, gated behind a `window.confirm` (irreversible from the UI). **Verified through real PDFium, not just this crate's own reader**: a page with two separate real-font text runs at known positions has one redacted, and PDFium's own character-extraction (`page_char_boxes`) confirms zero characters remain in the redacted region while the untouched run survives intact, plus a rendered-pixel check confirming the region is visually solid black — the actual "true removal" proof a naive cover-with-a-box redaction would fail. Known limitations (documented in the crate's module doc, not hidden): approximate (not exact-glyph-metric) text bounding boxes, no partial-glyph/partial-path redaction (whole operator dropped or kept, never split), clipping paths (`W`/`W*`) not applied, and metadata/hidden-content sanitization (PLAN.md's "sanitize (PDF4QT port)" half of this milestone) not implemented — only on-page visible content is addressed.
- **M6 license plumbing scaffold (activation deferred, per decision log — nothing gates on this):** `openpdfedit-license`'s existing Ed25519 offline `verify()` (from M0) gained a matching `sign()`, exercised by a new `examples/mint_dev_license.rs` and two new tests (a genuinely random keypair round-trip, and a JSON-serialize-then-verify round trip, on top of the existing fixed-key-vector tests). Two Tauri commands (`import_license_cmd`, `get_license_status_cmd`) persist an imported, verified license into the app's own data directory (re-verified on every status read, not just trusted from import) and a header badge shows the current tier ("Free" until one's imported). **The OpenApps checkout/entitlement-issuance integration is NOT built** — there is no live purchasing backend to integrate with from this environment, and PLAN.md's M6 scope explicitly separates that ("platform M7") from this app's own license-plumbing half. `DEV_OPENAPPS_PUBLIC_KEY` in `apps/desktop/src-tauri/src/license.rs` is a clearly-labeled placeholder keypair (private half public in `mint_dev_license.rs`) standing in for a real platform-issued trust root — swapping in the real one is the only change needed once that integration exists.
- **M7 in-place editing MVP ("the moat," scoped way down from its full ambition — see below):** new `openpdfedit-textedit` crate, built almost entirely by *composing* M4/M5's already-shipped primitives rather than a new engine: `list_text_runs`/`list_image_placements` walk a page's content stream (the same graphics-state-tracking approach `openpdfedit-redact` uses, but *collecting* runs with their exact rendering matrix instead of dropping overlapping ones); `edit_text_run` removes the old run via `openpdfedit_redact::redact_content` (the exact same "true removal" call redaction uses — reused, not reimplemented) then appends new text at the *original run's exact rendering matrix* using the *same font resource* (no new `/Resources` entry needed), with a `Tz` horizontal-scale adjustment that approximately fits the new text into the old run's estimated width (a real, spec-legal technique for a like-for-like footprint without real glyph metrics — see the crate's module doc for exactly why this isn't glyph-accurate reflow); `move_image` removes the old `Do` call the same way and re-emits it under a translated `cm`. Four new Tauri commands (`list_text_runs_cmd`/`edit_text_run_cmd`/`list_image_placements_cmd`/`move_image_cmd`, runs/placements identified by index into a freshly re-listed array, not by resending float coordinates that could drift through JSON) plus two new click-based tools ("Edit Text," "Move Image") in the toolbar. **Verified through real PDFium**: a page with real Helvetica text has one run's text replaced with a longer string, and PDFium's own character extraction (`page_char_boxes`) confirms exactly the new text's character count is present (not the old count, not old+new combined) after an incremental save/reopen round trip. **What "the moat" actually needs that this does not provide** (see the crate's module doc for the full writeup): real embedded-font glyph metrics (parsing the TrueType/CFF program) instead of the character-count approximation, font subsetting/merging (the `subsetter` crate PLAN.md names), and paragraph-level reflow (Tier-3 in PLAN.md's own tiering, explicitly deferred even in the full spec) — this MVP is genuinely "fix a typo, change a date" on a run that's its own complete `Tj`/`TJ` call, not a substitute for reflowing a wrapped paragraph.
- **M8 PAdES signing: BLOCKED, deliberately not attempted.** Real PDF signing needs constructing a valid DER-encoded CMS/PKCS#7 `SignedData` structure (required for interop with *any* real-world validator, including PDFium itself and Acrobat — a non-standard signature format would validate nowhere, defeating the point) plus OS-keystore/PKCS#12 private-key access (`PLAN.md`'s own spec) — cross-platform, security-sensitive, and, per the *same* investigation that blocked M5's verification half, resting on RustCrypto's `cms` crate, which was still pre-release (`0.3.0-pre.2`) at the time of that investigation. The failure mode of a subtly-wrong signing implementation is the mirror image of a subtly-wrong verifier: a signature that looks present but doesn't validate anywhere, or — worse — one built on a mishandled private key. Same call as M5, same reasoning: don't ship a security-sensitive feature this size half-built. Tracked as a standing TODO alongside M5's, to revisit together once the `cms` ecosystem has matured.
- **M8 form-field *creation* (the inverse of M4's form-fill):** two new `openpdfedit-doc` primitives, `merge_acroform_entries` and `ensure_acroform_and_append_field` (sharing a private `find_or_create_acroform` helper — the AcroForm-level counterpart to `append_annotation_ref`'s page-level `/Annots` append, same "array may be direct or indirect" handling). New `openpdfedit-forms` crate: `create_field` builds a Widget-annotation-is-its-own-field dictionary (Text or Checkbox — the two kinds M4's own fill-side testing already found reliable; RadioButton groups and ComboBox/ListBox are out of scope, matching M4's own documented gaps), registers it via `append_annotation_ref` (literally the same call `openpdfedit-annot` uses) and the two new AcroForm primitives, and — for Text fields — merges a Helvetica `/DR`/`/DA` into `/AcroForm` so the field's default appearance string has a font to resolve. One Tauri command (`create_form_field_cmd`, via `commit_mutation`) plus two new drag-rectangle toolbar tools ("Add Text Field," "Add Checkbox"). **Verified through real PDFium — and specifically through M4's own already-tested fill machinery, not a fresh assertion**: a field created here is independently recognized by `PdfiumEngine::list_form_fields` (name, type, initial state all correct), then filled through the *existing*, already-verified `fill_form_fields`/`save_document` path, and the filled value round-trips through a save/reopen — proof a field created by this new code is genuinely usable by the rest of the app, not just structurally present.
- **M9 batch pipelines, PII redaction, document compare, and CLI (all built by composing already-shipped crates, not new engine code):** new `openpdfedit-batch` crate — `PiiPattern` (Email/UsSsn/UsPhone/CardNumber16, plain hand-written regexes, explicitly documented as "catch the obvious, structurally-regular cases," not a comprehensive NLP/NER-grade PII detector) and `redact_pii(doc, patterns)`, which finds matching text runs via M7's `list_text_runs` and true-removes each one via M5's `redact_page` (reused as-is, not reimplemented) plus `merge_files`, a thin `openpdfedit-pages::merge` wrapper for headless use where there's no already-open engine handle. **Verified through real PDFium**: an email address next to unrelated text is redacted, and PDFium's own character extraction confirms zero leaked characters in the redacted line's position while the unrelated line survives. New `openpdfedit-compare` crate, two independent modes: `compare_text` diffs per-page text runs between two documents via a hand-rolled LCS sequence diff (no PDFium needed — pure content-stream reading, usable headlessly); `compare_pixels` renders both documents page-by-page through an `Engine` and reports a per-page differing-pixel count plus bounding box (skips pages that don't render at matching dimensions rather than guessing). **Verified through real PDFium**: identical documents produce zero pixel differences; a document with one shape moved produces a non-zero diff whose bounding box lands where the shape actually moved to. New `openpdfedit-cli` binary (`apps/cli`) — hand-rolled argument parsing (no `clap`; two-to-three subcommands with a handful of args each doesn't need a parsing framework, and it keeps the license-policy surface minimal), subcommands `redact-pii`, `merge`, and `compare` (text-mode only — the CLI deliberately has no PDFium dependency, so pixel-mode compare isn't available from it), tested end-to-end against real generated PDFs including a full CLI-entry-point round trip. One new Tauri command (`compare_documents_cmd`, `apps/desktop/src-tauri/src/compare.rs`) exposes both compare modes to the desktop app — takes two file paths directly (the documents being compared don't need to already be open), runs text-mode unconditionally and pixel-mode only if a render width is requested, opens/closes its own short-lived engine handles for the pixel pass rather than polluting `AppState::docs` — plus a "Compare…" toolbar button that picks a second file and shows a summary via dialog. **PDF/A convert/validate and full release engineering (auto-update, code-signing/notarization on both OSes, installers, website, docs) are deliberately not attempted** — no mature, independently-verifiable Rust PDF/A validator was evaluated for this pass (the same "don't ship what can't be tested here" standard applied throughout this log), and release engineering needs signing certificates and distribution infrastructure this sandboxed dev environment doesn't have access to; both are tracked as standing follow-ups rather than shipped half-built.
- **Post-M9 real-usage bugfix pass (2026-08-02), found via actually installing and running the packaged release build — not caught by any automated test until these fixes added coverage for them):** (1) **The packaged app couldn't render any PDF at all**: `tile://` responses lacked CORS headers, so the webview (loading from `tauri://localhost`) silently discarded every tile response before JS ever saw it — confirmed live via Safari Web Inspector showing "Origin tauri://localhost is not allowed by Access-Control-Allow-Origin" despite the Rust handler returning real 200s. Fixed by adding `Access-Control-Allow-Origin` to every `tile_response` branch and `Access-Control-Expose-Headers` for the custom `X-Tile-Width`/`X-Tile-Height` headers (which aren't on CORS's default-exposed allowlist either — same mechanism, second bite). (2) **Pages went white again after scrolling out of view and back**: `PdfPage.svelte`'s "already painted" cache flag wasn't reset when its `<canvas>` was destroyed (intentional, for memory, once a page scrolls far enough away), so a freshly-recreated blank canvas was never repainted. (3) **Text-run bounding boxes were roughly 2x too wide** for real-world PDFs using 2-byte/CID-encoded embedded fonts (confirmed on an external real resume PDF) — the width approximation counted lossy-UTF8-decoded characters, which silently doubles for byte-pairs where each byte is independently valid UTF-8; fixed with a heuristic that detects the "every other byte is 0x00" shape and halves the estimate. (4) Highlight/underline/strikeout's live drag preview showed the same translucent box for all three tools, even though underline/strikeout render as thin lines once saved — fixed the preview to show a line for those two tools instead. **Undo/redo added**: whole-file byte snapshots keyed by path (survives the handle-rotation every edit does), capped at 20 steps, covering every mutating command uniformly (annotations, page ops, redaction, text/image edits, field creation, form fill, OCR) — `undo_cmd`/`redo_cmd` Tauri commands, ⌘Z/⌘⇧Z shortcuts, toolbar buttons gated on new `OpenedDocument.can_undo`/`can_redo` fields, with a real multi-step round-trip test (not just "the command returned Ok"). All confirmed via direct PDFium rendering of real-world PDFs and real end-to-end round-trip tests, not just unit tests against synthetic fixtures — see git history for the investigation trail (bbox-overlay rendering, click-detection coverage sweeps).
- **Real text selection + annotation deletion added (2026-08-02), replacing the freehand-rectangle-only markup gesture:** highlight/underline/strikeout previously created annotations from whatever raw rectangle the user dragged, with no awareness of where the actual text was, and there was no way to select or delete an existing annotation at all — both reported directly from real usage. Fixed with two new pure-geometry primitives in `openpdfedit-engine` (`nearest_char_index`, `char_range_to_line_quads`), built on `page_char_boxes`'s real PDFium character extraction (not this codebase's own approximate content-stream interpreter): a drag gesture's two endpoints snap to the nearest real character, and the character range between them groups into one bounding quad per visual line — multi-line selections now produce multiple correctly-shaped quads instead of one box spanning the gap between lines. A drag that lands more than `SELECTION_SNAP_MARGIN` (20pt) from any character returns no selection rather than snapping to distant, unrelated text. New `text_selection_quads_cmd` Tauri command wires this into `+page.svelte`'s `handleCreateAnnotation`. Deletion: new `Document::remove_annotation_ref`/`openpdfedit_annot::delete_annotation` (unlinks from `/Annots`; the annotation object itself is left orphaned, the same trade-off `openpdfedit-forms`' font merging already makes elsewhere rather than building real mark-and-sweep GC) plus a `delete_annotation_cmd`, surfaced via a "select" tool that was previously a complete no-op — click an existing annotation while it's active, confirm, delete. `AnnotationSummaryDto` gained a stable `id` (the real lopdf object id) so delete targets exactly the annotation that was clicked, not a fragile array position. All verified through real PDFium: a real Helvetica text-page test proves a loose drag rectangle snaps tightly to the actual glyph bounds (not the input rectangle) and correctly returns nothing when dragged far from any text; a real add-two/delete-one/list round trip proves the surviving annotation is exactly the untargeted one, through an actual incremental-save-and-reparse cycle.
- **Subset-font text editing implemented properly (2026-08-02) — correcting a wrong earlier conclusion.** A previous pass decided that text in embedded *subset* fonts "can't be edited" and shipped a refusal dialog. That was wrong, and since virtually every real-world PDF (Google Docs, Word, LaTeX, Pages) uses `Identity-H` subset fonts, it made the edit feature useless on essentially every document a user actually has — reported directly, correctly, as unacceptable given Acrobat handles these fine. The missing piece was the font's **`/ToUnicode` CMap**, which those PDFs carry precisely so text can be copied/searched: read forwards it turns glyph ids into real text; read *backwards* it turns typed characters back into glyph ids, which is what makes writing possible. New `openpdfedit-textedit::font` module implements a real CMap parser (`beginbfchar`, both `beginbfrange` forms, multi-code-unit UTF-16BE destinations), the inverse mapping for encoding, and `/W`+`/DW` glyph widths so run bounding boxes use **true** metrics instead of the old character-count guess. New `Document::page_font_resources`/`decoded_stream`/`resolve` primitives expose what's needed. Two further fidelity fixes fell out of testing against real files: `TJ` kerning adjustments beyond a threshold are now read back as **word spaces** (otherwise text extracted as `"DeJianK."`), and consecutive runs sharing font/size/baseline are **merged** into one editable unit (Google Docs emits one `Tj` per character — without merging, clicking a word offered a single letter; a real exported report went from 502 unusable per-character runs to 16 real editable lines). Verified against the user's own two real PDFs, not just synthetic fixtures: a Google Docs export (502→16 runs, 100% editable, correct spacing) and a resume (96/98 editable — the two exceptions are icon-font glyphs with no `/ToUnicode`, correctly flagged), plus an end-to-end edit round-tripped through real PDFium on both. The remaining honest limit is now narrow and specific rather than blanket: a subset only embeds glyphs the document actually used, so a character appearing nowhere in the original has no glyph to point at — `FontInfo::encode` reports exactly which characters those are and the UI names them.
- **Appearance-fidelity bugfix pass (2026-08-03), all four reported from real use of the installed build and all four invisible to the existing tests** — every one of them was a *rendering* defect on documents whose structure was already correct, which is exactly what extraction-based assertions cannot see. The lasting change is methodological: this pass added the project's first tests that render through PDFium and count pixels. (1) **Editing text on a coloured background changed its colour, or made it vanish.** The content-stream walker tracked only the CTM through `q`/`Q`, so a run's fill colour was never captured, and `edit_text_run` appended replacement text with no colour operator at all — meaning it always drew in the PDF default, pure black. White text on a dark banner became black-on-dark, i.e. gone. Fixed by tracking the *whole* graphics state (fill colour, `Tr`, `Tc`, `Tw`, `Tz`) through the `q`/`Q` stack and replaying it around the replacement. Colour is captured as the original operators (`cs`+`scn`, `rg`, `k`, …) rather than a decoded RGB triple, so resource-defined colour spaces this crate can't interpret — ICCBased, Separation, Indexed, patterns — reproduce exactly. Runs of differing colour no longer merge into one editable unit, which would have recoloured text the user never touched. (2) **Text couldn't be moved, only images could.** New `move_text_run` relocates a run by replaying its original text-showing operators verbatim under a translated `Tm` — no decode, no re-encode — so glyphs, kerning, font and colour all survive bit-exactly, and a run whose font has no `/ToUnicode` (uneditable by definition) can still be moved, because relocating text never requires reading it. Both move tools became **drag gestures** with a live offset readout, replacing the old "type dx,dy into a prompt" flow that gave no feedback about which direction was which. (3) **A created checkbox wasn't a checkbox.** `create_field` gave every field a single `/AP` `/N` stream; a checkbox's `/N` must be a *dictionary of appearance states* keyed by the names `/AS`/`/V` use, so with one stream there was no ticked appearance to select and the widget was a static box forever. Now ships real `/Off` and `/Yes` states, squares the freehand drag (a wide rectangle reads as a text box), and registers `/ZaDb` for viewers that synthesize their own appearance. Two adjacent defects fell out: `merge_acroform_entries` overwrote `/DR` wholesale, so adding a checkbox after a text field dropped the text field's font — and adding *any* field to a document that already had a real form would have discarded that form's fonts, breaking its existing fields; new `Document::ensure_acroform_font` merges into the nested `/Font` dict instead. And `pdfium-render`'s `set_checked` writes `/AS` as the *string* `(/Yes)` via `FPDFAnnot_SetStringValue`, which matches no appearance-state key, so ticking a box through the fill path never rendered a tick; `normalize_button_states` repairs string-valued button `/AS`//`/V` back to names after every PDFium save. (4) **OCR failed with "tesseract is not installed or not on PATH" on a machine where it was installed.** A GUI app launched from Finder inherits `PATH=/usr/bin:/bin:/usr/sbin:/sbin` — Homebrew's prefix is not on it. `tesseract_path()` now checks an `OPENPDFEDIT_TESSERACT` override, then `PATH`, then the standard install prefixes for Homebrew (both architectures), MacPorts, apt, snap and the Windows installer; the failure message names what to install and how, instead of an errno. Regression test empties `PATH` to reproduce the Finder environment exactly.
- **Test suite:** 28 test binaries (197 individual tests), all green — `cargo fmt`, `cargo clippy --workspace --all-targets -D warnings`, `cargo deny check`, `cargo test --workspace`, `svelte-check`, and a production Vite build all pass with zero failures/warnings as of the last full run.
- **Five real bugs found via deliberate concurrency/edge-case/library-boundary testing, not by luck:** (1) `EngineHandle`'s `Drop` impl sent a shutdown signal on *every* clone's drop, not just the last — dropping one short-lived clone (e.g. a worker thread) silently killed the shared render thread for every other clone still in use, including the app's primary handle; fixed by removing the custom `Drop` and relying on `mpsc::Sender`'s built-in "last sender dropped" semantics. (2) `lopdf::IncrementalDocument::save_to` allocates its own object id from `new_document.max_id` during save, which manual `.objects.insert()` calls (the only way to reuse an already-known id) never bumped — under the right circumstances this let `save_to`'s own bookkeeping object silently overwrite the very object an edit had just written, corrupting the save with no error. (3) The lopdf encryption bug above. (4) **PDFium's `save_to_file()` cannot safely write back to the same path a document is still open from** — it doesn't error, it crashes the *process* with a native trap; discovered while testing forms fill (which naturally saves back to the file it just opened). Fixed by always saving to a sibling temp file and atomically renaming it into place, so PDFium's writer never touches a path it currently has open for reading — see `forms.rs`'s `fill_form_fields_impl` doc. (5) The RadioButton `/V`-lands-on-the-wrong-object issue above. All five are documented in code comments and in gstack learnings.

**Known verification gap:** this sandboxed environment has no screen-capture/accessibility access, so anything requiring *visually* driving the app (does a highlight actually appear where dragged, does the comments panel render correctly, 60fps scroll, sub-500ms cold start) is unverified by direct observation — only by process-level evidence (the app launches, registers a window, boots with all M2 commands registered) and automated tests exercising the underlying engine/render-thread/cache/annotation layers against real multi-page PDFs and real PDFium. Worth a manual pass on a real desktop session before trusting the interactive/visual claims.

## 1. Executive summary

Build a **fast, dual-native (Windows + macOS), offline-first, open-source PDF editor** with a Rust core, monetized through the OpenApps platform in this same repo: a generous free tier plus a **genuinely perpetual, offline-verifiable personal license** for pro features, with org/team subscriptions later.

**Does Rust make sense? Yes — as a hybrid.** The research verdict is clear: use PDFium (BSD-3, Chrome's engine) for rendering behind a swappable engine trait, and Rust-native permissive crates (lopdf, pdf-writer/krilla, cosmic-text, RustCrypto) for everything else. A pure-Rust renderer (hayro) is 1–2 years from production grade and can slot in later. The hard problems (in-place text editing, PAdES signing, appearance streams) are PDF-domain problems you would face in any language — and Rust is the only ecosystem that covers every layer with permissive licenses, which the open-core model requires. Two shipped Tauri+PDFium open-source editors (Slate, Open PDF Studio) prove the exact stack.

**Why this can win.** Every major competitor commits at least two of four trust failures: fake "lifetime" licenses, forced cloud upload, account walls/nags, and closed-source opacity. Nobody ships PDF-XChange's feature depth with PDF Expert's polish on *both* Windows and macOS. And recurring Ask-HN threads confirm no trustworthy full-featured open-source PDF editor exists — Stirling PDF's 77k stars *without* real text editing shows the size of that hole.

## 3. Feature list and tiering

**Note (per decision log): all features below are developed ungated; the free/premium assignments are provisional market guidance for a tiering decision made later.** Derived from the Acrobat tier matrix and the 32-feature market free/paid analysis (`docs/research/02-competitors.md` §2). The market's paywall sits at *"change what the document says"* and *"do it at scale"*; markup/reading is free everywhere. Our twist: **free OCR and free basic redaction** as adoption wedges (PDF-XChange proved free OCR drives adoption; redaction is a privacy-audience magnet and CrabPDF validated the positioning).

### Free tier (open-source, no account, no watermark, no limits)

**Viewing & navigation**
- Tabs, continuous/single/two-up/presentation modes, dark mode (with page-color inversion), thumbnails, outline/bookmarks panel, layers (OCG) toggle, attachments panel
- Text selection with proper cursor/word/paragraph semantics, search with result list + highlight-all, zoom/fit modes, rotation
- Go-to-page, back/forward history, session restore, recent files, keyboard-first navigation
- Print (with page-range/scale options)

**Annotation & markup (full set — free everywhere in the market)**
- Highlight/underline/strikethrough/squiggly, sticky notes, free text, callouts
- Ink/freehand with smoothing, shapes (rect/ellipse/line/arrow/polygon), stamps (standard + custom image)
- Comments panel: threads/replies, status, filter/sort; import/export XFDF; flatten annotations; comment summary export

**Forms (fill)**
- Fill AcroForms (text, checkbox, radio, dropdown, list, date), save; flatten; basic field JS (calculate/format) — scoped subset, sandboxed
- Fill & Sign: draw/type/image signature placement (not cryptographic)

**Pages & files**
- Merge/split, reorder/rotate/delete/insert/extract pages, crop
- Compress/optimize (image downsampling presets, object/xref streams)
- Encrypt (AES-256) / remove password (with password), permissions
- Create PDF from images; export pages as images; basic metadata editing

**OCR (adoption wedge — free)**
- Single-document OCR with invisible text layer (platform-native engines: Apple Vision on macOS, Windows.Media.Ocr on Windows; Tesseract/RapidOCR fallback for quality + CJK)

**Redaction, basic (privacy wedge — free)**
- Manual mark-region/mark-text → apply with true content removal + metadata sanitize. (Pattern search-and-redact, redaction codes, and batch redact are premium.)

**Signatures (verify)**
- Full signature validation UI: chain to AATL/EUTL trust lists (public, downloadable), timestamps, modification detection, clear valid/invalid/warnings — free, because verification builds the trust story (Adobe's Reader plays the same game)

### Premium tier — "OpenPdfEdit Pro" (perpetual personal license, target **$59–79 one-time**, includes 2 years of updates; license verifies offline)

- **Edit text in place** — staged: (T2) line/text-box editing with font-subset merging and an *explicit* "font substituted" indicator; (T3, later) paragraph-level re-layout. The single clearest thing people pay for in this market.
- **Edit images/objects** — replace/crop/rotate/move/delete; add images/links/headers/footers/watermarks/page numbers/Bates numbering
- **Create fillable forms** — field palette, auto-detect from layout, properties, tab order, calculations/validation
- **Advanced redaction** — search-and-redact (regex + built-in PII patterns: SSN/phone/email/IBAN), redaction codes, batch redact, redaction log/certificate
- **Certificate signing (PAdES)** — sign with PKCS#12/OS-keystore/smartcard identities, visible signatures, RFC 3161 timestamps; B-B/B-T at launch, LT/LTA follow-up; certify-with-permissions later
- **Document compare** — side-by-side + change report (text and pixel modes)
- **Batch processing** — run any tool over folders (OCR, compress, convert, watermark, encrypt); saved pipelines; CLI companion binary
- **Conversion** — PDF↔Office: local best-effort via bundled converters (v1 is local-only per decision log; optional clearly-labeled cloud fidelity service revisited post-1.0); PDF→text/HTML/images local
- **PDF/A** — convert + validate (archival)
- **Scanner integration** (TWAIN/ICA/WIA) with scan-to-OCR pipeline

### Later / org tier (subscription via OpenApps, not in v1 scope)
- Multi-seat licensing/admin, SSO, deployment tooling (MSI/MDM), audit
- E-sign request workflows (send-for-signature, audit trail) — envelope-metered
- Optional AI (summarize/chat/AI-redact) — **opt-in, off by default, local-model option**; never a button that can't be hidden (Adobe's forced-AI backlash is a gift; don't repeat it)
- Accessibility tagging/PDF/UA checker (underserved; Acrobat's auto-tagging is weak — possible differentiator earlier if demand shows)
- Measuring tools (CAD/construction niche)

### Free-vs-premium rationale
Free tier ≈ everything Preview + Foxit Reader + web tools offer, minus nothing (no watermarks, no caps, no account) — plus OCR and basic redaction, which most competitors gate. That's the adoption engine and the open-source goodwill. Premium = the market-proven "change what the document says / at scale" cluster. This undercuts Acrobat Standard ($179/yr) and Nitro ($250 fake-perpetual) with a real $59–79 perpetual, matches PDF-XChange's proven price point, and the open-source core makes "yours forever" credible in a way no competitor can copy (the Affinity lesson: open source is the hedge against price-zeroing acquirers).

## 4. Business model & OpenApps integration

OpenPdfEdit becomes the **first real app on the OpenApps platform** (this monorepo: credits ledger, Stripe/Lightning/ETH rails, EdDSA JWT sessions with local JWKS verification — M1–M8 complete).

- **Purchase flow:** in-app "Buy Pro" → OpenApps checkout (Stripe primary; Lightning/ETH as differentiators for the privacy audience — pay for a privacy tool without a card). Sale settles through the existing credit ledger.
- **Entitlement:** on purchase, the server issues a **signed offline license file** (Ed25519, same key discipline as the platform's JWKS): `{license_id, user_or_anon_purchase_id, tier, issued_at, updates_until}`. The app verifies the signature locally — **no phone-home required to keep working, ever**. Optional online activation only for cross-device convenience.
- **Updates policy:** perpetual license = that major version forever + 2 years of updates; renewing updates is optional and discounted. (PDF-XChange's maintenance model, which sustained a company 20+ years.)
- **Anonymous purchase path:** license keyed to a purchase receipt, not an account — "no account required" extends even to paying customers where rails allow.
- **Work item this creates:** the OpenApps **Tauri 2 plugin** (platform milestone M7, currently not started) — checkout window, entitlement fetch, license-file storage. OpenPdfEdit is its first consumer; build it as `sdk/tauri` in the platform tree.
- **Licensing structure of the code:** core + free features MIT/Apache dual (matches workspace); premium features live in a separate non-OSS-licensed directory à la Stirling (`app/proprietary/` precedent) — honest open-core, clearly separated. Decision needed (see §10): fully-open Aseprite-style (everything source-available, binaries paid) vs. open-core split.

> **Superseded (2026-08-25).** Most of this section describes a design that was not built. What shipped instead is the credit ledger and a single server-verified entitlement — no signed offline licence file, no Tauri plugin, no proprietary directory, no perpetual-licence or anonymous-purchase path. See §11.2 for what was actually decided and why. This section is kept as the record of what was planned, not as a description of the product.

**Pixel path (the performance-critical detail):** render tiles on the Rust side, deliver to the webview via a custom URI scheme/response — never JSON IPC — composite in canvas/WebGL with virtualized pages; selection/hit-testing from PDFium char boxes computed in Rust.

## 6. Architecture

Separate Cargo workspace at `openpdfedit/` (do not entangle with the platform workspace's release cadence; platform is a path-dependency for shared code only if ever needed).

```
openpdfedit/
├── Cargo.toml                  # workspace
├── crates/
│   ├── openpdfedit-engine/         # Engine trait: render tiles, text geometry, form fill
│   │   └── (pdfium backend feature; hayro backend later)
│   ├── openpdfedit-doc/            # document model: lopdf wrapper, incremental save
│   │   #  pipeline, undo/redo (command journal), object surgery
│   ├── openpdfedit-annot/          # annotation model + appearance-stream generation
│   ├── openpdfedit-forms/          # AcroForm create/edit; sandboxed field-JS subset
│   ├── openpdfedit-pages/          # merge/split/rotate/crop/compress/optimize (qpdf FFI)
│   ├── openpdfedit-ocr/            # engine trait (vision/winocr/tesseract) + sandwich layer
│   ├── openpdfedit-sign/           # PAdES: CMS assembly, trust lists (AATL/EUTL), verify
│   ├── openpdfedit-redact/         # mark → apply true removal + sanitize (PDF4QT port)
│   ├── openpdfedit-textedit/       # [premium] run clustering, line editing, subset merge
│   ├── openpdfedit-compare/        # [premium] text + raster diff
│   ├── openpdfedit-batch/          # [premium] pipeline runner (also powers the CLI)
│   └── openpdfedit-license/        # Ed25519 offline license verify + OpenApps client
├── apps/
│   ├── desktop/                # Tauri 2 app (src-tauri + web front-end)
│   └── cli/                    # openpdfedit-cli: batch ops headless (premium unlock)
└── docs/
```

**Key invariants**
1. **Incremental-save discipline:** any edit to a signed document appends an incremental update; the UI surfaces "this will invalidate signatures" only for operations that must rewrite.
2. **Engine trait boundary:** nothing outside `openpdfedit-engine` may touch PDFium types. This is what makes the hayro migration and the bus-factor story real.
3. **Undo/redo as a command journal** over document mutations (not byte snapshots), replayable → also gives crash recovery.
4. **All parsing hostile-input hardened:** PDFs are an attack surface; fuzz `openpdfedit-doc` and the engine boundary from day one.
5. **Renderer on its own thread** with an LRU tile cache keyed by (page, zoom, generation); generation bumps on edit.

**M7 — Text & image editing (the moat; 6–10 wks, premium).** Tier-2 in-place editing: run clustering from char geometry, line/text-box edit, font-subset merge via `subsetter`, explicit substitution indicator; image replace/crop/move; links/headers/footers/watermarks/Bates. **M8 — PAdES signing + form creation (4–6 wks, premium).** Sign with OS-keystore/PKCS#12 identities, visible signatures, timestamps (B-B/B-T); form-field creation palette with auto-detect.

*Accept:* 1.0 launch: HN/Product Hunt-ready with the benchmark story (startup time, binary size, 2,000-page open) measured and reproducible.

## 9. Testing & quality strategy

- **Corpus testing:** pdf.js + PDFBox test suites (hayro already validated this path: 1,400+ PDFs) + a scraped wild-PDF corpus; render-diff against PDFium reference images; parse-don't-crash on 100%.
- **Property tests:** open→edit→incremental-save→reopen invariants (objects preserved, signatures intact, xref valid); ledger-style discipline like the platform's `openapps-core`.
- **Fuzzing:** cargo-fuzz on parsers (content streams, xref, fonts) in CI; PDFs are a real attack surface and "memory-safe PDF editor" is part of the pitch.
- **Conformance oracles:** Adobe Reader (render + signature acceptance), EU DSS (signature validity), veraPDF external binary (PDF/A), qpdf --check (structure).
- **Perf budgets in CI:** cold start, open-time on reference docs, tile latency, memory ceiling — regressions fail the build (performance is a headline feature; treat it like correctness).
- **Redaction verification:** automated post-redaction extraction sweep (text, images, metadata, attachments, JS) must return zero hits — this check itself becomes a marketable trust feature.

Display/product branding only — the crate prefixes (`openpdfedit-*`), the workspace directory, and the `openpdfedit` CLI binary stay lowercase-kebab, matching ordinary Rust/npm package-naming convention.
2. **Open-core structure.** RESOLVED (2026-08-25), and not the way this section anticipated. One feature is gated — the watermark tool — and it is gated *at the entitlement*, not at the source: the code stays in this repository under the same MIT/Apache dual licence as everything else. No `app/proprietary/` split, and the signed-offline-licence design in §4 is unbuilt and unused.

   What actually ships is the OpenApps credit ledger: the app asks `/v1/credits/entitlement` whether this account has redeemed `openpdfedit_supporter_unlock`, and openapps-gateway is the only thing that can charge for it. Server-verified rather than locally-verified, which is the opposite of §4's "no phone-home required to keep working, ever" — a deliberate trade, since it is one optional tool rather than the product, and every other feature works with no account and no network.

   The honest consequence: because the watermark source is public and permissively licensed, anyone can build an unlocked copy. The gate is a request, not a wall. It is worth having anyway — the people who would compile their own were never going to pay, and the ones who would pay are not inconvenienced — but it should not be mistaken for enforcement. `WATERMARK_IS_PREMIUM` in `apps/desktop/src/lib/openapps.ts` reverses it in one line.

   Also worth recording: the tool shipped **free in v0.1.1–v0.1.4** and was gated in v0.1.5. Taking something back is a real cost, paid once.
3. **Pricing.** RESOLVED (2026-08-25): 1,000 credits, charged once, per account rather than per device — the entitlement is a server fact, so reinstalling or switching machines costs nothing further. Not a subscription and not per document. Matches OpenCapture's Supporter unlock exactly, deliberately: two products with the same shape of purchase should not teach a user two different models.
4. **Front-end framework within Tauri:** RESOLVED: **Svelte 5**. Fine-grained reactivity fits editor-style UI (many small independent panels/state slices — tool palettes, page thumbnails, annotation properties) better than React's re-render model; ~30–40% less boilerplate; smallest runtime, which matters for the "instant, tiny binary" positioning. Traded off: thinner component ecosystem than React (expect to hand-roll more a11y primitives — virtualized lists, comboboxes, dialogs), smaller contributor pool, and Svelte 5 runes are new enough that AI-assisted code generation and Stack Overflow coverage lag React's. Mitigation: keep UI logic thin and push state/behavior into Rust/Tauri commands wherever practical, so the front-end framework stays a rendering shell, not the source of truth.
5. **Cloud conversion.** RESOLVED: local-only in v1; cloud fidelity service revisited post-1.0.
